# 中文风格与结构

## 文章骨架

```markdown
# 标题：一个具体动作 + 一个结构性后果（不超过 30 字）

---

**摘要**：第一段交代背景与旧认知；第二段交代本文做了什么（语料/实验/样本量）；第三段给数字结论，至少两个比例。不写「本文将」。

**关键词**：AI 安全、提示注入、Agent 配置、权限提升、持久化、MCP、代码审计

---

## 一、具体事件/场景开头

时间、编号、厂商、研究者、原始链接。先给最小事实，再给影响。

| 项 | 值 |
|---|---|
| CVE | … |
| CVSS | … |
| 披露日期 | … |
| 修复 | … |

## 二、机制：和旧问题差在哪

一张对照表，逐维比较。不要先讲大道理。

## 三、数据：我们查了什么

采集方法、样本量、分类口径、命中数、比例、多重命中说明。

## 四、实验：三种做法分别挡住多少

变量、对照组、输出表。

## 五、为什么

把机制讲透，引用真实代码/配置/轨迹原文。

## 六、影响面与迁移

这个落点还会出现在哪些工具/场景。

## 七、检测与防御

给可直接运行的检查脚本或清单。

## 八、边界

主动交代样本偏差、因果限制、未覆盖项。

## 九、部署清单

分优先级、可勾选。

## 十、结语

回到开头的具体事件，回答「谁该在什么时候做什么」。不写展望。

---
```

## 段落与句子

- 长短交错：一段 2–4 句，下一段可以 1 句。段落长度 CV ≥ 0.5。
- 一句只做一个判断。避免从句套从句。
- 数字后面紧跟单位与口径：「40.6%（106/261 个配置）」，不要只写「四成」。
- 术语第一次出现给英文原文：`落点（placement）`、`审批疲劳（approval fatigue）`。
- 引用原文用块引用或代码块，并给中文解释；不要用机器翻译冒充原文。

## 表格

- 每章至少一张。
- 表头用中文；数字列右对齐 `---:`。
- 重点数字加粗，但一张表不超过 2 处。
- 表后必须有一句话解读，不能丢下表就走。

## 代码块

- 一律带语言标识：`python` / `json` / `bash` / `text` / `dockerfile` / `c`。
- 正文引用的脚本用 `<<SRC>>` 回填，保证与磁盘逐字一致。
- 终端输出用 `text`，保留原始缩进与错误信息。
- 代码块前后各空一行；不要放在表格中间。

## 用词替换表

| 别写 | 改写 |
|---|---|
| 极大地提升了 | 从 13% 提到 47% |
| 有效防御了 | 拦下 7/15 个载荷 |
| 众所周知 | （删掉，直接给事实） |
| 研究表明 | 论文 X（arXiv:…）第 N 节统计了… |
| 值得注意的是 | （删掉，把句子改成判断句） |
| 这也意味着 | 因此 / 具体来说 |
| 我们需要认识到 | （删掉，直接写该做什么） |

## 标题

三种可用结构：

1. **具体动作 + 结构性后果**：「Agent 把自己写成了后门：一次提示注入如何变成持久的权限提升」
2. **数据 + 反常识结论**：「多 Agent 流水线的静默继承：7497 条真实失败轨迹中的验证缺口」
3. **产品/编号 + 机制**：「OpenSSH 8.1 到 10.6：一个被读错 25 年的密码比较」

不用「浅谈」「初探」「从…看…」「XXX 的分析与思考」。

## 结语

三句话：回到开头的具体事件；指出仍然没有人负责的那一环；给一条读者明天就能执行的动作。不写展望，不写口号。
