# 八阶段流水线

## 阶段 0：选题与立项

选题只接受三类交集，至少占两类：

1. **新落点**：同类漏洞的影响面从 A 搬到了 B（上下文 → 磁盘配置、单 Agent → 多 Agent、一次调用 → 持久记忆）。
2. **有数据**：能拿到公开语料、真实轨迹、CVE 列表、厂商公告，且能自己统计。
3. **能复现**：读者用公开工具和自己电脑就能跑，不需要 GPU、账号或内网。

立项时先写三样东西：

- **一句话卖点**：不超过 80 字，含一个反常识数字。
- **章节表**：# / 章节 / 核心内容 / 本章表 / 本章图。
- **数据源与靶场**：数据从哪来，实验放哪个目录，预计跑多久。

反例：纯新闻复述、纯观点、只翻译论文、无法给出原始数据的「某机构统计」。

## 阶段 1：外部事实核实

建一张表，逐条登记：

| 事实 | 来源 | 状态 |
|---|---|---|
| CVE 编号、CVSS、向量 | NVD / 厂商公告 | 已核实 |
| 披露日期、报告日期、修复日期 | 厂商公告 / 研究者博客 | 已核实 |
| 修复方式 | commit / patch diff | 已核实 |
| 论文结论、数据集规模 | arXiv / 官方仓库 | 已核实（下载并统计） |

规则：

- 一手来源优先：厂商公告 > NVD > 安全媒体 > 二手博客。
- 数字必须能点回原文；不能点回的，写「据报道」并降权使用。
- 拉源码优先 `https://cdn.jsdelivr.net/gh/<repo>@<ref>/<file>`，GitHub API 会限流。
- 外部数字统一放进 `external_numbers.txt`，一行一条，注明来源 URL。

## 阶段 2：建立靶场

目录：`_lab_<slug>/`

```
_lab_<slug>/
├── DESIGN.md            # 实验目的、变量、预期、失败判据
├── collect_*.py         # 采集（如需要）
├── exp_*.py             # 实验（每个实验一个脚本）
├── out_*.txt / out_*.json
├── snips/               # 正文要引用的代码片段
├── gen_svg_*.py         # 配图脚本
├── svg2png_*.js
└── svgkit.py            # 绘图库副本
```

要求：

- **最小复现**先跑通，再做对照。对照组与实验组只差一个变量。
- 每个脚本顶部写清用途、输入、输出、运行方式；退出码 0/1 可用于 CI。
- 实验输出同时落盘为 `out_*.txt`，正文只引用文件内容。
- 实验设计写成 DESIGN.md：假设、变量、样本量、判定标准、已知偏差。

实验设计常见缺陷，要在正文「边界」一章主动交代：

- 观察性数据不能证明因果；
- 语料来自 GitHub 公开仓库，存在筛选偏差；
- 样本量小，比例波动大；
- 缺少对照组；
- 标注依赖单一来源。

## 阶段 3：数据采集与统计

### 语料采集

- 用 GitHub Code Search 按文件名 + 键名组合查询，查询清单显式写在脚本里。
- **落盘文件名必须带仓库名**：`<kind>__<owner_repo>__<path with _>`。
  否则不同仓库的同名文件会互相覆盖，样本数会莫名减少。
- 维护 `corpus_index.json`：`kind / repo / path / branch / size / file`。
- 分批跑：用 `QSET=0:5` 环境变量切段，单次不超过 1 分钟；脚本支持续跑。
- 采集后先做完整性检查：索引条数 == 落盘文件数，缺一类要显式记录「本轮未覆盖」。

### 统计

- 每个比例写清**分子/分母**，分母是「全部样本」还是「失败样本」要说明。
- 分类脚本与正文表格使用同一份输出，不手工改数。
- 多重命中（同一文件命中多类）要单独统计「兼有」比例，不能简单相加。
- 小数统一保留一位；百分比之和不为 100% 时注明「可多重命中」。

### 引文与轨迹

逐条读原始数据时，保留原文英文句子 + 中文解释。案例章节必须能定位到具体文件、行号或 trace id。

## 阶段 4：分章起草

- 按章节表拆成 `_part_<slug>1.md`、`_part_<slug>2.md`…，每部分 2–4 章。
- 每章结构：一个具体场景/数据入口 → 一张表 → 机制解释 → 边界或反例。
- 代码块先用占位：

  ````
  ```python
  # <<SRC:_lab_x/exp_survey.py>>
  ```
  ````

  构建时自动替换为磁盘原文。手写块只用于命令与真实终端输出。
- 正文不要写「本节将介绍」；直接给事实。
- 每写完一部分立刻跑 `humanizer_scan.py`，不要攒到最后。

## 阶段 5：配图

见 `references/figures.md`。原则：

- 每图一个论点，图内标题就是论点。
- 图必须能被正文一句话引用；alt 写这句引用。
- 优先顺序：白底机制图 > 数据条形/矩阵 > 时间线 > 真实截图 > 终端输出。
- 真实截图要加红框与来源条；终端图必须是真实运行输出。

## 阶段 6：合并与回填

```bash
python scripts/build_article.py articles/x.md _part_x1.md _part_x2.md _part_x3.md
```

脚本做三件事：

1. 按顺序拼接分章；
2. 把所有 `# <<SRC:path>>` 占位替换为磁盘文件原文；
3. 打印字符数、章数、表数、代码块、图数、破折号、段落/句长 CV。

回填后**不要再手改代码块**；要改就改磁盘源文件再 build。

## 阶段 7：终检

按 `references/quality-gates.md` 全部跑一遍。顺序：

```bash
python scripts/article_gate.py articles/x.md
python scripts/humanizer_scan.py articles/x.md
python scripts/reader_path.py articles/x.md --repro "_lab_x/exp_survey.py:_lab_x/out_survey.txt"
```

有问题就回到对应阶段修，不要在成稿上直接打补丁掩盖。

## 阶段 8：发布

见 `references/publishing.md`。流程：推 CDN → 验证 200 → 校对 MD 无本地路径 → 填投稿清单 → 粘贴发布。

## 时间预算（单人）

| 阶段 | 典型耗时 |
|---|---|---|
| 选题 + 事实核实 | 2–4 h |
| 靶场与实验 | 4–12 h |
| 数据统计 | 2–6 h |
| 起草（每章 2–3k 字） | 6–10 h |
| 配图（6–13 张） | 3–6 h |
| 终检与修 | 1–3 h |
| 发布 | 0.5 h |

数据驱动的文章，**一半时间应该花在阶段 1–3**；写作只是把已经成立的事实排好。
